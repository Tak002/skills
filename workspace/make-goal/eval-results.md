## 실행 검증 (명령 허용, 문제지 밖)

평가 suffix 는 명령 실행을 막으므로 검사 루프를 보려면 문제지 밖에서 돌려야 한다. 스킬 사본만 `.claude/skills/` 에 둔 빈 임시 폴더에서 `claude -p "/make-goal …" --dangerously-skip-permissions --output-format stream-json` 로 두 번 돌리고 transcript 의 tool 호출을 셌다 (2026-09-30).

| 실행 | 입력 | `check_goal.py` 호출 | 흐름 | 시간 |
| --- | --- | --- | --- | --- |
| A | 문제 3 요청(엔드포인트 18개) | 3회 | 첫 초안부터 런처 + 명세(`docs/goals/2026-09-30-api-v2-migration.md`, 체크리스트 23항목) → 3,249자 통과 → 명세 작성 뒤 재검사 → C 항목 정규식 수정 뒤 3,250자 통과 | 444초 |
| B | 4,523자 초안(examples 2번 + 긴 `[참고]`·`[범위 밖]`)을 "다듬어줘" | 2회 | 4,523자 `[length]` 오류 → 사다리 1단계(`[참고]` 2,973 → 758자, 사실은 유지) → 2,521자 통과. 출력 `· 검사 통과 · 반복 2회`, 완료 조건·제약 유지 | 236초 |

- 초과 → 사다리 → 재검사 루프가 실제로 돈다. 사다리 순서(판정 대상이 아닌 `[참고]` 부터)도 지켰다.
- 두 실행 모두 초안을 프로젝트 밖 임시 파일(`mktemp -d`)에 쓰고 검사했다.

## 발견과 조치

- **with-skill 이 낸 goal 10개가 모두 실제 `check_goal.py` 를 오류·경고 0 으로 통과했다.** 평가에서는 Bash 가 막혀 모델이 검사를 돌리지 못하므로, 응답에서 goal 을 뽑아 따로 검사했다.

  | 회차 | 문제 1 | 문제 2 (Claude · Codex) | 문제 3 (런처) |
  | --- | --- | --- | --- |
  | 1 | 2,433 | 2,713 · 2,637 | 3,168 |
  | 2 | 2,342 | 타임아웃 | 2,970 |
  | 3 | 2,872 | 2,837 · 2,565 | 3,016 |

  모델은 매번 "검사 미실행 · 추정치" 라고 밝혔고, "검사 통과" 라고 쓰지 않았다(주의 절의 정직성 규칙). 추정치는 실제와 2–170자 차이였다.
- **baseline 의 가장 큰 실패는 사용자의 5,000자 오해를 그대로 따른 것이다.** 문제 3 에서 세 번 모두 "5,000자 제한에는 여유가 있다" 고 답했다. with-skill 은 세 번 모두 "Claude Code·Codex 는 4,000자, 5,000자는 OpenChamber" 로 바로잡았다.
- baseline 이 부족한 점은 다음과 같다.
  - /goal 을 알고 재현 테스트부터 쓰게 하는 등 방향은 맞다.
  - 하지만 C 항목별 확인 명령과 기대값, 마지막 턴 재검증, BLOCKED/STOPPED·턴 상한이 없다. 금지 조항은 문장뿐이다.
  - Codex 조정(턴 상한 대신 token budget, blocked 3턴 규칙)은 세 번 모두 없었다.
  - 문제 2 에서는 /goal 조건문 대신 긴 Markdown 작업 지시서를 썼다. 두 벌을 따로 낸 기준 1개만 통과했다.
- baseline 의 문제 3 goal 은 2,800–2,965자로 4,000 안에 들었다. 차이는 길이보다 구조다.
  - baseline 은 엔드포인트별 요구 18행을 한 덩어리 안에서 압축했다.
  - with-skill 은 요구를 명세 파일(R1–R26 체크리스트)에 그대로 두었다. 런처는 `grep -c '^- \[ \]' <명세>` → `0` 으로 확인하게 했다.
  - with-skill 은 세 번 모두 "첫 초안이 제한의 1.5배 이상 → 사다리를 건너뛰고 런처 + 명세" 규칙을 적용했다고 설명했다.
- **문제지 수정 (첫 실행 전)**: 문제 3 의 첫 문안(엔드포인트 목록 + 규칙)은 두 가지 방식 모두로 4,000자 안에 들어갈 수 있었다. 직접 짜 본 런처가 약 2,000자였고, 압축한 한 덩어리 goal 도 가능했다. 그러면 "런처 + 명세" 기준이 부당하게 FAIL 할 수 있다.
  - 첫 실행을 중단했다. 결과 파일이 생기기 전이라 빈 iteration 폴더를 지웠다.
  - 엔드포인트별 변경 표 18행을 넣어 분리가 필요한 요청으로 바꿨다.
  - 규칙끼리의 모순(소프트 삭제 vs 스키마 변경 금지)도 뺐다. 모순이 있으면 스킬이 질문하는 쪽으로 가는 것이 맞는 동작이라 기준이 흔들리기 때문이다.
- **응답 시간이 길다.** with-skill 은 252–655초, baseline 은 62–323초였다.
  - 2회차 문제 2(`both`)는 600초를 넘겨 빈 응답이 됐다. 3회차는 `--timeout 1200` 으로 돌렸다.
  - 처음에는 손으로 글자를 세느라 늦는다고 보고 주의 절에 "섹션별 어림(±10%)" 규칙을 넣었다. 모델은 규칙을 따랐지만(응답에 "섹션별 어림 추정치") 시간은 줄지 않았다(문제 2 655초, 문제 3 637초).
  - 시간은 게이밍 차단 설계와 긴 응답(6–13k자)에 쓰인다. 예를 들어 moment 출력 golden 파일을 `git hash-object` 로 고정하고, 봉투 형식과 RFC 7807 의 충돌을 찾아 기본값을 정했다.
  - 실제 사용에서는 `check_goal.py` 가 세고 검사하므로 손 대조 시간은 빠진다. 다음 평가도 `--timeout 1200` 을 쓴다.
- 채점 오류는 없었다. `grading.txt` 의 근거는 모두 응답의 구체 문장을 인용했다.
